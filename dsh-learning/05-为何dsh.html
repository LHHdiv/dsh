你说过：希望 dsh 以后成为你**终身迭代、更新、属于你个人的 Agent**；但目前它比较简单，你还不懂、不知道怎么处理。

🎯
本文学系目标理解 dsh 的「插件化」架构为何适合作为你终身迭代、更新的个人 Agent。

第5章 为什么选 dsh 做终身个人 Agent

前面四章铺垫完毕。这一章回答你最关心的问题：为什么是 dsh，而不是别的框架，来做你终身迭代的个人 Agent？

5.1 你的目标是什么

你说过：希望 dsh 以后成为你终身迭代、更新、属于你个人的 Agent；但目前它比较简单，你还不懂、不知道怎么处理。

这其实是个好起点。一个"简单且架构清晰"的项目，比一个"庞大但混乱"的项目更适合学习和个人演进。关键看它的架构是否允许你平滑地往上长东西。

5.2 终身迭代需要的三件事

要让一个 Agent 陪你走十年，它必须具备：

  1. 可扩展：你能不断加新能力（工具、记忆、子 Agent），而不把代码改成一团乱麻。
  2. 可回滚：新加的东西出问题，能干净地撤掉，不影响其它部分。
  3. 可理解：你（未来可能的专业版你）能读懂它，知道改哪里、为什么。

5.3 dsh 如何满足这三点

可扩展：一切皆插件

dsh 的每个能力都是一个 Cordis 插件。想加一个"读我的笔记"的工具？新建一个插件包，注册到 ctx.tools，核心代码一行不用动。新增能力 = 挂插件，不是改核心。

对比：在"改核心"的架构里，每加一个工具你可能要改 5 个文件、还容易破坏别人；在 dsh 里，你只写你自己的包。

可回滚：注册是可逆 effect

插件通过 ctx.effect() / ctx.on() 注册能力，卸载或重载时统一回滚。你加的 my_notes 工具，本质是往工具表插了一行；撤掉插件，这行就消失，不留痕迹。这让"试错"变得安全——而试错，是终身学习的常态。

可理解：分层清晰、命名诚实

dsh 的目录按"能力"分包（core/、llm/、tools、preset、session……），每个包只拥有自己那一块（ctx key）。读源码时，你能清楚地问："这一行注册了什么？挂在哪个 ctx 上？"——这种局部可理解性，正是非专业开发者能否真正"学会"的关键。

5.4 一个反例提醒

有些框架把"智能"写死在核心循环里，你每想改一点行为，都得 fork 核心、和上游分道扬镳。当上游更新，你的改动就被淹没。

dsh 的插件化让你始终站在上游之上扩展：上游升级，你的插件大多还能用。这正是"终身"二字的工程含义。

5.5 所以，路线图应该是这样的

你现在 ──► 学会它（本书 Part 0~2）
            │
            ▼
   在它之上加能力（Part 3）
   · 私有工具（你已做 my_notes）
   · 个人知识库 / 长期记忆
   · 多 Agent 协作
   · 终身自治（自我改进）
            │
            ▼
   它成为「你的」Agent，且随时能跟随上游升级

5.6 小结

  • 终身个人 Agent 需要：可扩展、可回滚、可理解。
  • dsh 的"一切皆插件 + 可逆 effect + 清晰分包"，恰好在架构层面满足这三点。
  • 因此它适合做你的底座；你只需要学会它、并在它之上长东西。
